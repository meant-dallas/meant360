Membership status is re-evaluated every time, including for a returning session — "Already signed in?" only skips re-authenticating, both its Yes and No branches always converge on the Membership check; status is never cached from whenever the user first signed in. Active and non-active member/spouse are two distinct paths, not one path with a side note: non-active always passes through the renewal-fee step before rejoining the exact same "existing registration?" check active members use — same downstream flow either way, and that fee requires real payment even on an otherwise-free event. Everything above "Which page?" is otherwise byte-for-byte identical for both flows; the only legitimate divergence is the final action, since registration and check-in are different actions (manage a paid commitment vs. mark attendance), not different access rules.

Per-persona expected flow

instantReturning user (any persona, valid session or guest-session cookie)

  • Chooser is never shown — only the authentication step is skipped.
  • The membership-status check always still runs, fresh, on every load. It's never cached from whenever the session was first created, since status (active/non-active, existing registration) can change between visits.

activeActive member

  • Sees the Google / Email chooser.
  • Google → succeeds immediately (their email resolves to role: 'member') → real, persistent NextAuth session.
  • Email → OTP sent and verified → scoped proof only, no persistent portal login created.
  • Membership status: active → goes straight to the existing-registration check, no renewal step.
  • Registration: existing registration found → manage/cancel; none found → create one. Check-in: existing registration found → check in; none found → walk-in.

activeSpouse (active)

  • Identical to the active-member case in every respect — a spouse's email is in the same lookup map (getMemberEmailMap(), auth.ts:64-70), so Google succeeds for them too.
  • Household-aware lookup finds the same registration regardless of which spouse it was filed under, with full view/modify/cancel/check-in access either way.

non-activeNon-active (expired) member or spouse

  • Google still succeeds — Member.status is never checked at the NextAuth role-resolution layer, only later during the membership-status check.
  • Email still works the same way as any other member/spouse.
  • This is its own distinct path, not a side note on the active path: membership status → non-active routes through a renewal-fee step, then rejoins the exact same existing-registration check the active path uses — same downstream flow, no detour, no dead end.
  • The renewal fee requires payment even when the event itself is free. A $0 event registration with an expired member still needs a payment step for the renewal amount — it's never silently waived just because the event has no cost of its own.

guestGuest, event allows guests

  • Sees the same chooser as everyone else — nothing marks them as different upfront.
  • Google → NextAuth denies (no member or spouse record, role: null) — but instead of an error, the server reads the event ID back out of the next-auth.callback-url cookie, silently sends an OTP to that same email for this event, and lands them directly on the code-entry step. No retyping, no "Access Denied."
  • Email → OTP sent the normal way.
  • Either path converges on the same scoped OTP verification → guest-policy check passes → proceeds exactly like the member case (manage/create on registration; check-in/walk-in on check-in).

blockedGuest, event does NOT allow guests

  • Same chooser, same silent Google→OTP handoff.
  • Guest-policy check fails → blocked with the same denial message, at the same point, on both pages.

out of scopeAdmin/committee staff acting as staff

  • Not part of this flow at all. Staff checking other attendees in or correcting a registration do it through the Event Dashboard's Manage Registration modal (ItemsEventDetail.tsx) — a separate, already-working surface.
  • When a staff member registers or checks in for themselves, they're just a member going through the member path above like anyone else.

Security boundary guest identity & authorization

A valid OTP proves control of an email address — it does not by itself prove ownership of a particular registration. Ownership is established separately by the household-aware match against the registration's known emails. The event ID recovered from the next-auth.callback-url cookie during the Google fallback is a routing hint only — which event's OTP-send to trigger — never an authorization input. It is not signed, not server-issued, and must never be trusted as proof of anything.

✓ Already enforced (verified against the code)

  • Guest proof is cryptographically bound to email + eventId + expiry via a signed HMAC (guest-session.ts:45-57) — can't be forged or replayed for a different email/event.
  • Cookie is httpOnly: true, secure in production, sameSite: 'lax' (guest-session.ts:50-56).
  • OTP expiry (10 minutes) and single-use enforcement both exist (items-otp/route.ts:135-150) — sending a new code invalidates any prior unused one for that email.

⬤ Gaps to close before shipping the Google fallback

  • No OTP attempt limit. handleVerify only checks email + code + used:false + expiresAt — nothing caps wrong-code attempts within a code's lifetime.
  • No per-email resend throttle. handleSend issues a fresh code on every call; the only protection is middleware's generic IP-based rate limit, which doesn't stop a distributed attempt.
  • An invalid eventId is silently ignored, not rejected — in one shared function, reachable from both entry points. handleSend does its own loose check, const catalog = event ? parseItemCatalog(event.items) : null — when event is null, the guest-policy check if (catalog && !catalog.allowGuests) is just skipped, not enforced. Note this is narrower than it first looks: handleVerify and handleSessionResume already fail closed correctly today, because both call lookupItemsRegistrant() → requireItemsEvent(eventId), which throws NotFoundError for a missing/wrong-model/deleted event (caught by the route and turned into a 404). Only handleSend skips that same guard. Since handleSend is the one function both normal email OTP (user types their own email) and the Google fallback (server-triggered send using the cookie-recovered eventId) would call, fixing it there — making it use requireItemsEvent(eventId) the same way handleVerify already does, instead of its own silent null-check — closes the gap for both entry points at once, not as two separate fixes.

Fix direction: in handleSend, replace the loose eventRepository.findById(eventId) + null-check with requireItemsEvent(eventId) (same guard handleVerify/handleSessionResume already use) so a bogus eventId throws NotFoundError → 404, rather than silently skipping the guest-policy check. Add a per-email attempt counter (lock out after N wrong tries) and a per-email resend cooldown to items-otp, independent of the existing IP-based limiter.

Security boundary write authorization vs. middleware

Middleware is a routing/access layer, not the final security boundary. Adding checkin-batch, participants, and walkin-checkin to the public passthrough only removes an over-restrictive gate that was blocking legitimate self-service callers — it does not remove or weaken the authorization check already inside each handler, which runs regardless of what middleware allows through.

✓ Already enforced (verified against the code)

  • Every write handler calls isRegistrationOwnerOrStaff() / hasValidGuestSession() itself, independent of the middleware gate — removing the middleware block doesn't touch this.
  • Ownership is checked against that specific registration's contactEmail, freshly fetched from the DB per request — not just "any valid cookie for this event." An unrelated guest's cookie, even for the same event, fails the email match.
  • Participant → registration binding is explicitly enforced in application code, not just implied: checkinItemsParticipant/checkinItemsParticipants both guard if (!participant || participant.registrationId !== registrationId) throw new NotFoundError('Participant') (event-items.service.ts:1413,1455) before any mutation runs — a participant ID from a different registration is rejected per-item, in the batch case too, not merely at the registration level. addWalkInAttendee never accepts a participant ID at all; it only ever creates fresh rows scoped to the given registrationId.
  • Registration → event binding — partially applied. if (!registration || registration.eventId !== params.eventId) return errorResponse('Registration not found', 404) is now in place on checkin, checkin-batch, and cancel. It does not expose one user's data to another even where it's still missing — the guest-session cookie's own eventId binding plus the contactEmail match already constrain the action to the caller's own registration — but it's a correctness gap wherever it's absent: a mismatched URL should fail outright rather than happen to be caught by an unrelated check.

⬤ Gaps to close

  • Registration → event binding — still missing on 2 of 5 routes. participants/route.ts (add walk-in attendee) and [registrationId]/route.ts (PATCH edit) still fetch registration = findById(registrationId) without the eventId check.
  • No negative tests exist, because no test suite exists. This repo has none configured at all (confirmed in CLAUDE.md: "No test suite is configured"). Adding "an unrelated user cannot invoke these routes" tests is the right ask, but it's a bigger prerequisite here than writing a few assertions — it means standing up a test framework first. Flagging honestly rather than treating it as a quick addition.

On action-level granularity (add participants / modify items / cancel / mark attendance treated as one access level, not four): deliberate, not an oversight — rule 01's "any member or their spouse" grants full household ownership once authorization passes, matching the "Full access" decision made earlier in this design. There is no household-member action that should be staff-only once ownership is established.

Common identity object

Today, Google and OTP resolve identity through two separate, independently-written lookups that happen to answer the same question — not one shared source of truth. That's the same class of divergence behind everything else in this doc: two code paths that can silently drift apart.

⬤ Before — two shapes, two lookups

  • NextAuth (getSessionRole()): { role: 'admin'|'committee'|'member'|null, email, memberId, authenticated }. memberId comes from getMemberEmailMap() in auth.ts.
  • OTP (lookupItemsRegistrant()): { isMember, memberId?, memberName?, allowGuests, existingRegistration, familyMembers, requiresRenewal, currentMembershipLevel? }. memberId comes from a separate inline Member + MemberSpouse query written directly inside this function.
  • No shared concept of role between them (OTP has no role at all), and two independent queries for the same underlying fact — a future fix to one (e.g. also checking loginEmail) can silently not apply to the other.

✓ After — one shared resolver

  • New resolveIdentity(email) in a neutral, low-level module (e.g. src/lib/identity.ts) both auth.ts and event-items.service.ts import — single query against OrgOfficer + Member + MemberSpouse, called from exactly one place.
  • Returns one shape: { email, kind: 'admin'|'committee'|'member'|'guest', memberId, memberName?, membershipStatus?, currentMembershipLevel? } — kind collapses the old role/isMember split into one discriminator every caller reads the same way.
  • getUserRole() becomes a thin wrapper mapping kind to the legacy UserRole type, so requireAuth()/middleware/everything already reading role keeps working unchanged.
  • lookupItemsRegistrant() calls resolveIdentity() for the base identity, then layers registration-specific fields (existingRegistration, familyMembers, requiresRenewal, allowGuests) on top — it stops doing its own Member/MemberSpouse query entirely.

Companion piece: a separate resolveHouseholdEmails(memberId) helper (member email + loginEmail + every spouse email) becomes the single source both lookupItemsRegistrant()'s widened search and the check-in-specific authorization check call for matching — the same function used to find a registration is now also the function used to authorize acting on it, which is what actually closes root cause #2 (spouse email vs. contactEmail mismatch), rather than fixing it as a one-off patch inside the authorization helper alone.

What changes from today

  • Lookup

    Drop the forCheckin flag in lookupItemsRegistrant() — always widen to household emails (member + loginEmail + spouse emails), used identically by registration and check-in. Fixes the duplicate-household-registration gap.

  • OTP gate

    Drop skipMemberCheck / requiresSignIn / isGoogleSignInEmail() in items-otp's handleSend. Email always works for everyone, members included — nothing forces a detour to sign-in anymore.

  • Renewal

    Drop check-in's hard-blocking renewal_required PaymentForm step. Non-active member/spouse becomes its own path that appends the renewal fee and rejoins the same existing-registration check active members use — on both pages. The renewal fee still requires a real payment step even when the event itself is free; only the event's own cost is ever silently skipped, never the renewal.

  • Google fallback

    On role === null, the signIn callback reads the next-auth.callback-url cookie (via cookies() from next/headers — confirmed callable in this execution context, since next-auth@4.24.13's own NextAuthRouteHandler already does exactly this to populate req.cookies), extracts the event ID, triggers that event's OTP-send for the same email, and redirects straight to the code-entry step — replacing today's generic /auth/signin?error=AccessDenied.

  • Middleware

    Add checkin-batch, participants, and walkin-checkin to the existing public passthrough list (root cause #1 in the check-in doc — unchanged by this unification, still needs fixing regardless).

  • OTP hardening

    Required alongside the Google fallback (see Security boundary above): validate the recovered eventId against a real event record before sending anything; add a per-email attempt limit on handleVerify and a per-email resend cooldown on handleSend, independent of the existing IP-based rate limiter.

  • Authorization

    One shared, household-aware ownership check (member/spouse's household OR a matching guest-session cookie) used identically by registration's and check-in's write routes. No staff/admin short-circuit needed on these specific routes — staff only ever act through the Dashboard.

  • ID binding

    Applied to checkin, checkin-batch, and cancel. Still needed on participants (add walk-in attendee) and [registrationId] PATCH (edit) — see Security boundary above. Closes a correctness gap even though the contactEmail + cookie-eventId binding already prevents cross-user exploitation today.

  • Identity

    Introduce resolveIdentity(email) and resolveHouseholdEmails(memberId) (see Common identity object above). auth.ts's getUserRole() and event-items.service.ts's lookupItemsRegistrant() both call these instead of each running their own independent Member/MemberSpouse query.
